# 余票监控 · Bilibili 会员购

[![License: MIT](https://img.shields.io/badge/License-MIT-yellow.svg)](LICENSE)
[![Node.js >= 18](https://img.shields.io/badge/node-%3E%3D18-brightgreen.svg)](https://nodejs.org/)

基于 [`bili_ticket` 签名算法](https://github.com/SocialSisterYi/bilibili-API-collect/blob/master/docs/misc/sign/bili_ticket.md) 的会员购余票监控工具，包含：

- **管理台** `/admin`：添加项目、勾选票档、调节节奏、看日志
- **直播大屏** `/`：纯黑背景，开售前是翻页时钟倒计时，开售后切余票列表，一键手动切换两个视图，适合 OBS 浏览器源

零第三方依赖，单端口 Node 服务。

---

## 快速开始

需要 **Node.js 18+**，无需 `npm install`（零依赖）：

```bash
git clone <你的仓库地址>
cd bili-ticket-monitor
node server.js          # 默认 3000 端口，可用 PORT 环境变量覆盖
```

打开 `http://localhost:3000/admin`，**默认口令 `admin`**。⚠️ 首次登录后请立即在「设置」中修改管理口令。可选的环境变量见 [`.env.example`](.env.example)。

> 若把服务暴露到公网，务必先改口令，并建议只通过带鉴权的管理入口访问；`data/` 目录存放登录 Cookie 与口令，请勿提交或公开。

## 使用流程

1. **解析项目**：把会员购详情页链接（如 `https://show.bilibili.com/platform/detail.html?id=1007693`）、**b23 短链**（`https://b23.tv/xxxxx`）、微信分享的整段文案，或纯数字 ID 粘进输入框，点「解析」。b23 短链会自动跟随 302 展开成真实链接并提取项目 ID，结果上方显示「短链 → 真实链接」；若短链指向的不是会员购项目页会明确提示。
2. **勾选票档**：解析结果按场次分组，勾选想盯的票档；可填「大屏显示别名」让大屏标题更简洁。
3. **自动开跑**：添加后监控立即启动，票档一旦从「售罄 / 未开售 / 停售」变成「有票」，大屏会红色描边闪烁 + 播报。
4. **按项目管理**：监控列表按**项目 ID** 分组，每组组头有一个总开关，可一键启用 / 停用该项目下的全部票档，状态即时同步监控调度。
5. **接 OBS**：在 OBS 里添加「浏览器」源，URL 填直播页地址，分辨率 1920×1080，即可直接推流。

## 大屏说明

### 开售前：翻页时钟

- 天 / 时 / 分 / 秒 四组翻页卡片，每秒翻转一次，最后 60 秒整体转红并加速闪动。
- 时间以**服务器时间**为基准下发（`serverNow`），避免主播机器时钟不准导致倒计时偏差。
- 多个目标取**最近一个未来开售**的场次显示。
- 归零瞬间：全屏红框闪烁 + 冲击波 + 「开 售」大字 + 提示音，随后自动切到余票列表。
- 如果同时存在「已开售有票」和「更晚开售」的目标，不占用全屏，而是在列表上方显示一条 `NEXT SALE` 小横条。

### 开售后：余票列表

- 列表**按项目 ID 分组**：每组开头是一条带项目色渐变背景的分组头（项目名 + `ID xxx` + 档数），组内票档沿用同色左边条，不同项目颜色不同，一眼可区分；整体仍是纵向列表。
- 项目名由分组头统一承载，票档行大字显示**票档名**、小字显示场次，不再每行重复长项目名，一屏能看更多票档。
- 纯黑底、大字号，按目标数量自动缩放行高（1–2 个目标时铺满全屏）。分组头与票档行**等高**，桌面轮播分页保持精确。
- 桌面端目标超过 6 个时自动翻页轮播（每 7 秒一屏）；**手机端改为可上下滑动的纵向列表**，不再轮播、不会被裁切。
- 有票的票档排在最前，带红色渐变高亮与脉动徽章。
- 页面不再显示日志，只保留到票时的闪屏与提示音。

### 视图切换（键盘）

大屏固定只有「开票倒计时」和「余票监控」两个视图，按键即时切换，切换后自动模式暂停（不会被新的票况自动拽走），直到开售瞬间强制回到余票列表。

| 按键 | 作用 |
| --- | --- |
| `Tab` / `空格` | 两个视图互相切换 |
| `←` `↑` / `1` / `C` | 切到开票倒计时 |
| `→` `↓` / `2` / `L` | 切到余票监控 |
| 点右上角「视图」按钮 | 同 `Tab` |

没有待开售场次时切到倒计时视图，会显示「暂无待开售场次」占位，而不是一排全 0 的数字。

### 手机端适配

宽度 ≤700px 时：顶部信息折行收紧、翻页时钟按窄屏缩小、余票列表切换为**原生惯性滚动**（`overflow-y:auto`），每行按内容自适应高度：分组头显示项目名（最多两行）、票档行突出票档名、场次小字在下，状态徽章竖排在右侧；列表顶部提示「共 N 项 · 上下滑动查看」。

刷新或从后台恢复（bfcache）时会重置 DOM 缓存、清除轮播位移并重连 SSE；`flex-shrink:0` 保证桌面端 18 行也不会被压缩到视口高度导致文字重叠。渲染异常时自动整体复位重试一次。

## 轮询节奏（核心）

不做无用功：**开售前完全不请求，只在开售前 1 分钟才启动**，到点高频，售罄转中频刷回流。

| 阶段 | 触发条件 | 默认间隔 | 说明 |
| --- | --- | --- | --- |
| 静默待开售 | 距开售 > 60 s | **零请求** | 不发任何接口请求，只本地倒计时；每 30 分钟自检一次时间（仍不请求） |
| 预热 | 距开售 ≤ 60 s | 1 s，最后 5 秒 200 ms | 提前就位，避免本地时钟误差 |
| 抢票 | **开售后 10 分钟内**且仍无票 | **100 ms** | 只在开票瞬间高频；超过 10 分钟一律转长尾 |
| 刷回流 | 开售后 30 分钟内**刚转售罄** | **500 ms** | 持续 **15 分钟**（可调）后转长尾 |
| 长尾 | 开售已久 / 请求失败 / 状态异常 | 5 s | 不停请求，只降频 |
| 风控冷却 | 接口返回 HTTP 412 且**熔断开启** | **零请求** | 全局熔断，可在管理台一键关闭，见下节 |
| 自适应降频 | 接口返回 HTTP 412 且**自适应启用** | 当前间隔 **×2**（最高 ×16） | 不中断监控的柔性降频，见下节 |
| 开售避让 | 某票档距开售 ≤ N 分钟（默认 5） | **零请求** | 暂停所有刷回流 / 长尾任务，只留即将开售项目自己的预热与抢票，见下节 |
| 观察 | 已抢到 / 当前有票 | 2 s | 观察余票数量变化 |

> **抢票模式不再是兜底**：早期版本把「已过开售时间 + 状态未知 / 请求失败」一律判定成抢票，于是 412 之后反而升到最高频，形成「412 → 高频重试 → 412」死循环。现在只有「开售后 10 分钟窗口内」才允许进入抢票，失败、异常、开售已久一律走 5 s 低频。

**静默模式的两个例外**（否则会误判）：

- 开始监控 / 服务重启时，每个项目仍会真实请求 **一次**，拿到权威状态作为基准，然后才进静默。
- 项目没有开售时间、或开售时间已过（正在卖 / 延迟开售）时不会静默，按正常节奏轮询。

**为什么要静默**：开售前几小时每 30 秒一次看起来频率不高，但挂一整天就是上千次请求，容易被 `-412` 风控盯上，真到开抢时反而被限流。把请求集中在开售前的 1 分钟，既省请求也降低被风控的概率。

**代价**：静默期发现不了「项目提前开售 / 临时改期」。如果怕这个，把「开售前开始请求」调大（最长 600 秒），或在管理台关掉静默退回低频轮询。

**关于回流窗口 15 分钟**：会员购下单后未支付的订单通常在 15 分钟释放，这也是回流票最集中的时段。窗口结束后不会停止请求，只是降到 5 秒一次长期观察。

**关于 100 ms 的实际速率**：调度按「请求发起时间」计时，会自动扣掉本次请求耗时。若单次请求耗时 80 ms，实际周期约 100 ms；若网络较慢（200 ms+），实际周期会接近请求耗时。管理台状态栏显示的是实际节奏。

### 412 全局风控熔断

B 站的 `-412 request was banned` 是**出口 IP 级**风控：一个项目被封，同 IP 的其他项目也会一起被拦。因此熔断是全局的（挂在 Monitor 上，不是单个 worker）：

| 行为 | 规则 |
| --- | --- |
| 触发 | 接口返回 HTTP 412 / `code=-412` / `request was banned` / 非 JSON 风控页 |
| 冷却 | 首次 **30 s**，连续触发指数翻倍，最长 **10 分钟**（带 ±15% 抖动） |
| 冷却期间 | **所有项目零请求**，大屏阶段显示「风控冷却 · Ns」 |
| 解除后 | 强制 **1 s 最小间隔持续 1 分钟**，之后才逐步回到配置节奏 |
| 降级计数 | 完整熬过恢复期才减 1，否则再撞 412 时冷却继续翻倍 |
| 普通失败 | 按绝对时长退避 **2 s → 4 s → … → 60 s**，不再乘配置间隔（20 ms 时旧算法最多只退到 160 ms，形同虚设） |

**防风控硬下限**：开售后 ≥100 ms、售罄后 ≥200 ms。低于此值保存时会按边界值生效并明确提示（不会静默改回）。20 ms 相当于单项目 50 次/秒，必然触发 412。

**强烈建议填入会员购 Cookie**（`SESSDATA` / `bili_jct`）：无登录态的高频请求是 412 最常见的诱因。Cookie 为空时，熔断日志会附带这条提示。

### 自适应轮询延迟（应对高峰期 412）

高峰期 B 站会短暂拉黑出口 IP —— 开售前请求抢票或其他敏感接口、短时间内大量请求都可能触发 412，**这是正常现象，不代表程序异常**。硬熔断会漏掉「解封瞬间释放的回流票」，因此提供**柔性降频**作为替代或补充：

| 行为 | 规则 |
| --- | --- |
| 启用 | 管理台「监控设置 → 412 风控策略」勾选「自适应轮询延迟」，即时生效、无需重启 |
| 命中 412 | 轮询间隔倍率 **×2**（1 → 2 → 4 → 8 → 16 封顶），同一轮并发 412 只调一档 |
| 生效方式 | `wait = max(原间隔, min(原间隔 × 倍率, 30 s))`，倍率是 Monitor 全局的，所有项目共享 |
| 恢复 | 连续 **12 次**请求正常后倍率 ×0.75 回落（16 → 12 → 9 → … → 1），日志逐档回告 |
| 不中断 | 全程持续请求，不进入零请求冷却；大屏阶段标签不变，只显示实际间隔变大 |
| 停用 | 取消勾选后倍率按 ×1 计算；状态行显示「已停用」 |

**与熔断的组合**：

- **默认两项都开**：命中 412 → 先全局零请求冷却，解封后按倍率低频恢复。
- **只留自适应**（推荐给更看重回流票的场景）：点「关闭 412 熔断」，此后 412 只拉长间隔、不再停止请求；「立即解除冷却」可清掉已有冷却并把倍率复位到 ×1。
- 两项都关：412 退化为普通失败的绝对时长退避，**不建议**。

管理台「412 风控策略」卡片实时显示熔断开关状态、自适应倍率、开售避让状态与当前冷却剩余秒数；熔断开关走独立接口，切换时会自动清掉残留冷却等级。

### 开售避让（自适应节流的第二条规则）

**开售前请求抢票或其他敏感接口、短时间大量请求最容易把出口 IP 拉黑**，而此时刷回流 / 长尾监控对抢票毫无帮助，只是白白叠加请求量。因此只要在避让窗口内，就让回流任务给开抢让路：

| 行为 | 规则 |
| --- | --- |
| 触发 | 全局扫描启用目标，存在 `saleStart` 落在 `(now, now + N 分钟]` 的票档（默认 **5 分钟**，可调 1–30） |
| 避让对象 | **所有没有未来开售场次**的项目（即正在刷回流 / 长尾的 worker），一律**零请求暂停**，阶段显示「开售避让」 |
| 不受影响 | 即将开售的项目自己照常走预热 / 抢票；有票的稳定观察也不受影响 |
| 自动恢复 | 到开售时刻窗口自动结束，回流任务按常规节奏恢复，无需人工干预 |
| 启用 | 管理台「监控设置 → 412 风控策略」勾选「开售避让」，即时生效、无需重启；分钟数改后点「保存设置」 |
| 停用 | 取消勾选后所有回流任务立即恢复；状态行显示「已停用」 |

> 与静默期配合：开售前 5 分钟起，回流任务被避让、即将开售项目仍在静默（距开售 > 60 s 时零请求），整个系统在这段时间几乎不发请求；只在开售前 60 秒由主角项目开始预热，把出口 IP 的请求量压到最低再开抢。

## 技术实现

### bili_ticket

每隔 3 天需要刷新一次，程序内存缓存并在到期前 1 小时自动更新：

```
ts       = 当前 UNIX 秒
hexsign  = hmac_sha256(key='XgwSnGZ1p', msg='ts' + ts)
POST https://api.bilibili.com/bapis/bilibili.api.ticket.v1.Ticket/GenWebTicket
     ?key_id=ec02&hexsign=...&context[ts]=...&csrf=<cookie 中的 bili_jct>
→ data.ticket 写入 Cookie: bili_ticket=...
```

### 余票数据

```
GET https://show.bilibili.com/api/ticket/project/getV2
    ?version=134&id={项目ID}&project_id={项目ID}&requestSource=pc-new
```

关键字段（扫描 80 个项目 / 261 个票档实测得出）：

| 字段 | 说明 |
| --- | --- |
| `data.screen_list[].ticket_list[]` | 场次下的票档列表 |
| `ticket_list[].sale_flag.number` | **1** 未开售 / **2** 预售中（唯一可下单）/ **3** 已停售 / **4** 已售罄 |
| `ticket_list[].clickable` | 按钮是否可点，与上面四个状态严格一致 |
| `ticket_list[].num` | 当前**可购份数**，被 `static_limit.num`（每单限购数）封顶，**不是总库存** |
| `ticket_list[].static_limit.num` | 每单限购数，普遍为 8 |
| `ticket_list[].is_sale` | 恒为 `1`，**不能**用来判断是否在售（坑） |

判定规则：

```
available = sale_flag.number == 2 且 num != 0 且 clickable != false
presale   = number == 1（或文案含 未开售 / 待开售 / 即将开售）
soldout   = number == 4、num == 0（或文案含 售罄 / 售完 / 缺货 / 无票）
off       = number == 3（或文案含 停售 / 已结束 / 下架 / 不可售）
其余      = unknown，一律不判为有票
```

**关于 `num` 的坑**：它只会在库存低于限购数时才反映真实剩余（如 `num=3, limit=8` 即「仅剩 3 张」）；当 `num == limit` 时只能说明「还有票」，不能读成「只剩 8 张」。所以大屏只在 `0 < num < limit` 时显示具体数字，否则统一显示「有票」。

**去抖**：接口偶发单帧抖动（风控、旧数据）会让状态瞬间翻转。高频阶段（≤3 s）要求**连续 2 次**观测一致才采信，低频阶段单次即采信，避免 100 ms 轮询把误报放大成刷屏告警。

**失败保护**：单次请求失败只给状态打 `stale` 标记，保留上一结论（大屏不会闪断）；连续失败 5 次才降级为「异常」。

### NTP 校时

大屏倒计时和「开售瞬间切 100ms」都要靠本机时钟，主播机器的系统时间常见偏差几百毫秒到几秒。程序内置 SNTP 客户端（纯 `dgram`，无第三方依赖）：

```
T1 本机发送 → T2 服务器收到 → T3 服务器发出 → T4 本机收到
offset = ((T2 - T1) + (T3 - T4)) / 2
```

- 并发请求 `ntp.aliyun.com` / `ntp.tencent.com` / `cn.pool.ntp.org` / `time.cloudflare.com`，取 **RTT 最小**的一台，剔除偏差 > 5 秒的异常样本。
- **开售前 60 秒自动校时一次**（每个开售时间只做一次，由 1.5 秒守护定时器判定，精度 ±1.5 秒，不依赖轮询间隔）。
- 监控启动时静默校一次，避免主机长期未校时导致一开屏就偏。
- 手动校时：管理台「时钟校准 NTP → 立即校时」，或 `POST /api/admin/ntp`。
- NTP 的 UDP 123 被防火墙拦截时，自动降级用 bilibili 接口返回的 `current_time` 兜底（精度 1 秒），管理台会标注来源。
- 校时只改变程序内部的 `clock.now()`（倒计时、阶段切换、日志时间都用它），**不会修改系统时间**。

### 轮询策略

- 同一项目下的多个票档合并为 **一次** 请求，按项目分组，每个项目独立调度。
- 低频阶段（待开售 / 观察 / 长尾）附加 ±15% 随机抖动，高频阶段（抢票 / 刷回流）严格按节奏。
- 请求失败不会中断监控，连续失败按**绝对时长** 2 s → 4 s → … → 60 s 退避；若是 412 风控则触发全局熔断（可在管理台关闭）与 / 或自适应降频，见上节。
- 开售前 N 分钟进入**避让窗口**：无未来场次的回流 / 长尾 worker 零请求暂停，只保留即将开售项目，开售后自动恢复，见上节。

## 配置项

| 配置 | 说明 |
| --- | --- |
| 时钟校准 | 开售前 60 秒自动 NTP 校时；启动时校一次；管理台可手动校时 |
| 开售前静默 | 距开售还很远时零请求，到「开售前开始请求」的时刻才启动；可关闭 |
| 抢票节奏 | 开售前静默 60 s / 开售后 100 ms / 售罄后 500 ms / 回流持续 15 分钟 / 有票观察 2 s，均可调 |
| 配置生效 | **保存后立即重算调度，无需重启**（含静默期）；超出允许范围的数值会明确提示实际采用值，不会静默改回 |
| 数值范围 | 开售后 **100**–5000 ms / 售罄后 **200**–10000 ms / 回流 0–240 分 / 待开售 1–600 s / 开售前预热 5–600 s / 有票观察 200–60000 ms（前两项为防 412 硬下限） |
| 会员购 Cookie | 可选。出现频繁请求失败时，填入登录后的 `SESSDATA` / `bili_jct` 更稳定 |
| 自适应轮询延迟 | 412 时自动把间隔翻倍（最高 ×16），连续 12 次正常后回落；勾选即时生效，可在管理台停用 |
| 开售避让 | 某票档即将开售时，提前 N 分钟（默认 5，1–30 可调）自动暂停所有刷回流 / 长尾监控，开售后自动恢复；勾选即时生效 |
| 412 全局熔断 | 命中 412 后所有项目零请求冷却；管理台「关闭 412 熔断」按钮可一键关闭，「立即解除冷却」清空当前冷却与倍率 |
| 按项目分组 | 管理台监控列表按项目 ID 分组，组头总开关一键启用 / 停用该项目全部票档；直播大屏同样按项目分组、用组色区分，仍是纵向列表 |
| 大屏标题 / 副标题 | 显示在直播页顶部 |
| 提示音 | 有新票时播放双音提示 |
| 服务重启后自动监控 | 重启容器后自动恢复轮询 |
| 管理口令 | `/admin` 的访问口令 |

数据保存在 `data/store.json`，删除该文件即可恢复初始状态。

## 目录结构

```
server.js           HTTP 服务、路由、SSE 推送
lib/bili.js         bili_ticket 签名 + 会员购接口封装 + b23 短链展开 / 项目 ID 解析
lib/monitor.js      轮询引擎、状态变化判定、告警日志
lib/store.js        配置与目标持久化
lib/visits.js       访问统计（PV / 独立访客）
public/live.html    直播大屏
public/admin.html   管理台
data/visits.json    访问统计明细（自动生成）
```

## 访问统计

管理台右下角「访问统计」卡片显示**累计 PV、累计独立访客（UV）、今日 PV/UV**，另有最近 14 天趋势与最近 20 条访问明细；也可直接请求 `GET /api/admin/visits`（需管理口令）。

- 只统计直播页与管理台的**页面打开**，接口轮询、SSE、静态资源、健康检查均不计入。
- UV 按 `IP + User-Agent` 哈希去重；本机回环与常见探针 UA 单独计为「探针」并排除，避免平台健康检查刷高数据。
- IP 在明细里做了脱敏（隐藏最后一段），不记录完整 UA，不采集任何个人身份信息。
- 统计从功能启用（服务重启）那一刻开始，**之前的访问无法追溯**。发布平台的分享链接本身不提供浏览量查询接口。

## 注意事项

- 本工具仅做余票状态查询，不包含下单、抢购逻辑。
- 请控制轮询频率，遵守平台规则；高频请求可能触发风控（返回 `-412` 等）。**高峰期 412 是 B 站对出口 IP 的短暂拉黑，属正常现象**：可启用「自适应轮询延迟」柔性降频，或关闭「412 全局熔断」避免硬停期间漏掉回流票。
- 若某个项目**开售时间早已过去且票档全售罄**，它仍会以 5 s 长尾持续观察，是封禁期间唯一还在发请求的项目。此时建议在管理台暂时禁用它，只保留待开售项目（零请求静默），出口 IP 的封禁会自然解除。
- 余票状态以接口返回为准，可能存在秒级延迟，不保证抢票成功率。

## 隐私与安全

- 登录 Cookie、管理口令、监控目标均保存在本地 `data/store.json`，该文件已被 `.gitignore` 排除，**不会进入仓库**；请勿手动提交或分享。
- 访客统计仅记录脱敏 IP（隐藏末段）与 UA 摘要，不采集个人身份信息。
- 公开的直播大屏不含任何管理接口；管理 API 需口令鉴权。
